## 一、 核心八股与深度追问

### 1. 缓存穿透、缓存击穿和缓存雪崩分别是什么，怎么解决？

用商品详情页举例，可以从“商品是否存在”和“有多少缓存同时失效”两个维度区分：

| 异常类型 | 核心现象 | 触发场景 | 核心解决方案 |
| --- | --- | --- | --- |
| **缓存穿透** | 数据在缓存和数据库中都**不存在** | 恶意攻击或爬虫批量查询无效 ID，每次请求都穿透到数据库 | ① 参数基础合法性校验；<br>② 对查不到的 key 短暂缓存空值（设置短 TTL）；<br>③ 请求量极大时使用布隆过滤器（Bloom Filter）在网关/应用层拦截。 |
| **缓存击穿** | 单个**热点 key** 过期，数据在数据库中存在 | 爆款秒杀商品缓存刚好到期，大量并发请求瞬间全部打到数据库 | ① **互斥锁（Mutex）**：只允许一个请求查库重建缓存，其余请求等待重试；<br>② **逻辑过期**：缓存不设物理 TTL，由后台异步协程/线程检测并提前刷新。 |
| **缓存雪崩** | **大量不同 key** 同时过期，或 Redis 集群宕机 | 大批量商品的缓存设置了相同的过期时间，或整机故障 | ① 过期时间加上随机漂移值（如 `base + rand(0~300)s`），打散失效点；<br>② 多级缓存（本地缓存 + 分布式缓存）；<br>③ 做好 Redis 高可用哨兵/集群架构，应用侧做好限流与降级。 |

**追问一：解决缓存击穿时，为什么拿到互斥锁后还要再查一次缓存（DCL 双重检查锁）？**

假设请求 A 与请求 B 同时发现缓存缺失，请求 A 抢先拿到了分布式锁，去查数据库并把数据回填到缓存。

当请求 B 阻塞等待后拿到锁时，缓存其实已经被请求 A 填充完成了。如果 B 拿到锁后不再次检查缓存就直接查库，那么后面所有排队的并发请求依然会串行把数据库重新查一遍，导致互斥锁完全失去削峰意义。因此，加锁后必须再次查缓存，命中则直接返回。

**追问二：如果不希望互斥锁阻塞其他用户的读请求，怎么做？**

可以采用**逻辑过期（Logical Expiration）**方案：
- 缓存内部存放实际数据以及一个自定义的“逻辑过期时间戳”，但 Redis 本身不设置物理 TTL（或者设得很长）。
- 读请求取出数据后，如果发现当前时间已超过逻辑过期时间，当前请求**依然先返回旧数据**保证高可用，同时异步发起一个后台任务去获取锁并刷新缓存。
- 这种方案以容忍短暂数据弱一致为代价，换取读请求零阻塞和极高的吞吐量。

### 2. 如何实现分页？

常规后端系统中有两种主流方案：管理后台需要直接跳页时使用**偏移量分页**；C 端无限滚动或时间线流使用**游标分页**。

#### 方案一：偏移量分页（Offset Pagination）

假设每页 20 条，查询某个用户按时间倒序的第 3 页订单：

```sql
SELECT id, created_at, amount
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;
```

偏移量计算公式为 `offset = (pageNum - 1) * pageSize`。排序时必须引入全局唯一键 `id` 作为 Tie-breaker（平局决胜），确保下单时间相同的记录也有确定的先后顺序。

**深分页的性能隐患**：
当查询页码极大时（例如 `LIMIT 20 OFFSET 100000`），MySQL 的执行逻辑是顺着二级索引找出前 100020 条数据并逐一回表读取行记录，然后再把前 100000 条白白丢弃。这会导致巨大的磁盘随机 IO 和 CPU 开销。

**深分页优化：延迟关联（Deferred Join）**
如果业务必须支持跳大页，可以通过子查询覆盖索引先完成分页，再回表获取完整列：

```sql
SELECT o.id, o.created_at, o.amount
FROM orders o
JOIN (
    SELECT id
    FROM orders
    WHERE user_id = :userId
    ORDER BY created_at DESC, id DESC
    LIMIT 20 OFFSET 100000
) t ON o.id = t.id;
```
内层子查询只扫描索引树中的 `id` 列，无需进行 100000 次无意义的回表，最终只有实际返回的 20 条记录才执行回表，耗时通常能降低数倍至数十倍。

#### 方案二：游标分页（Seek Method / Cursor-based Pagination）

第一页按时间和 ID 倒序取 20 条，把上一页最后一条记录的 `created_at` 和 `id` 作为游标，查询下一页时直接从该游标之后定位：

```sql
SELECT id, created_at, amount
FROM orders
WHERE user_id = :userId
  AND (
      created_at < :lastTime
      OR (created_at = :lastTime AND id < :lastId)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**核心优势与局限**：
- **性能恒定**：配合联合索引 `(user_id, created_at, id)`，查询始终是常数级（走索引直接 Seek 到目标位置），无论翻到多少页性能完全一致。
- **避免错页**：如果在用户翻页过程中有新订单插入，不会像偏移量分页那样把旧数据挤到下一页造成重复显示。
- **局限性**：无法支持任意指定页码的跳转（如“直接跳转到第 50 页”），仅适用于瀑布流、移动端下拉刷新或纯上一页/下一页场景。

> **小技巧**：如果前端需要判断“是否还有下一页”，查询时可以请求 `LIMIT 21`。如果返回了 21 条，说明还有下一页，实际只给前端返回前 20 条，并将第 20 条作为下一次查询的游标。

### 3. 消息队列如何保证幂等？

幂等是指同一操作发起一次或多次执行，产生的影响是相同的。在分布式系统中，由于网络抖动、客户端重试或消费者处理完成但在提交 ACK 前宕机，消息被重复投递是常态，因此消费者必须实现幂等。

#### 场景一：消费逻辑属于数据库本地操作（强一致场景）

以“每笔支付成功发放一次积分”为例，最稳妥的方案是**业务唯一索引 + 本地事务**：

1. **建立唯一约束**：在积分流水表上为 `(payment_id, reward_type)` 建立联合唯一索引。
2. **原子事务执行**：消费者开启数据库事务，先向积分流水表插入记录，随后更新用户积分余额。
3. **提交并确认**：两步均执行成功后提交事务，随后向 MQ 返回 ACK。
4. **重试处理**：若重复消息到达，插入流水时触发 `DuplicateKeyException` 唯一键冲突异常，捕获该异常后直接提交事务并向 MQ 发送 ACK，阻断后续重复积分发放。

**为什么必须放在同一个事务中？**
如果先加积分再写流水，一旦加积分成功但流水写入失败，重试时又会重复加积分；反之若先单独提交流水再加积分失败，重试会被流水幂等拦截，导致用户少发积分。两步必须具备 ACID 原子性。

#### 场景二：消费逻辑包含外部 RPC 或非事务操作

如果消费逻辑涉及调用第三方接口（如发货、调用银行退款、发送短信通知），无法依赖本地数据库事务，常用的方案包括：

- **状态机前置条件检查（CAS 思想）**：
  若更新实体具备单向状态机，更新时加入前置条件：
  ```sql
  UPDATE orders SET status = 'PAID' WHERE id = :orderId AND status = 'PENDING';
  ```
  如果 `affected_rows == 0`，说明该订单已被处理或状态已流转，直接跳过业务并返回 ACK。
- **分布式锁 / 消费防重表（Token 机制）**：
  利用 Redis 的 `SET NX EX` 配合全局业务流水号，在处理前尝试占位。占位失败说明正有相同消息在并发执行或已被处理，直接忽略。

### 4. 数据库和 Redis 不一致怎么解决？

工业界最主流的基础模式是**旁路缓存（Cache Aside Pattern）**，以数据库作为权威真实数据源（Source of Truth）：

- **读取流程**：先查 Redis。命中则直接返回；未命中则查 MySQL，并将结果回填到 Redis，附带合理的 TTL。
- **写入流程**：**先更新 MySQL，事务提交成功后，再删除对应的 Redis 缓存**。

#### 关键追问与深度解析

**追问一：为什么必须“先更新数据库，再删除缓存”，而不是“先删缓存，再更数据库”？**

如果采用**先删缓存再改数据库**：
1. 请求 A 执行写操作，删除了缓存；
2. 此时并发的读请求 B 到来，发现缓存缺失，去数据库读取旧值（尚未更新）；
3. 请求 B 将读取到的旧值写入缓存；
4. 请求 A 随后才完成数据库的更新。
结果是数据库变成了新值，但 Redis 重新装填了旧值，且在 TTL 到期前旧数据会长久驻留。

如果采用**先更数据库再删缓存**：
只有在“缓存刚好失效 + 读请求查完库尚未写缓存 + 写请求更新完库并删完缓存 + 读请求随后把旧值填入缓存”这种极端严苛的并发时序下才会短暂不一致。由于写库耗时通常远大于读缓存写入，发生的概率极低。

**追问二：延迟双删（Delayed Double Delete）真的靠谱吗？**

有人提出先删缓存、更新库、休眠一会儿再删一次缓存（延迟双删）。在真实的微服务分布式环境下，这个方案存在明显缺陷：
- **休眠时间（Sleep）无法准确评估**：网络抖动、从库同步延迟或 GC 停顿都会导致预估的时间窗口失效；
- **阻塞调用线程**：同步休眠会占用工作线程，降低系统吞吐量。

**追问三：如果数据库更新成功，但删除缓存失败，导致旧数据残留怎么办？**

- **异步重试保障（Canal / Flink CDC 方案）**：业务代码只管更新 MySQL，不直接同步删缓存；利用 Canal 伪装成从库订阅 MySQL 的 `binlog`，收到对应表的提交变更后，将待删除 key 投递到消息队列，由消费者异步执行删除，失败依赖 MQ 的重试和死信队列机制兜底。
- **兜底防护**：所有缓存键严格配置 TTL（Time To Live），即便出现极端不一致，也能在过期后自动修复。

### 5. 数据库如果要分库，怎么处理？

分库前首先要进行瓶颈界定：若单表行数多但总容量和写入 QPS 不高，**分表**即可解决 B+ 树层级过高的问题；若单机磁盘容量告急、或单机连接数与写入吞吐触达物理硬件上限，才需要考虑**分库**。

- **垂直分库**：按微服务业务边界拆分（如用户库、商品库、订单库），各个库独立部署和扩容。
- **水平分库**：将同一种数据模型按特定路由规则打散到多个物理数据库中。

以电商最核心的**订单库水平分库**为例，必须攻关以下四个核心环节：

#### 1. 分片键（Sharding Key）的设计
分片键决定了数据路由逻辑。在电商场景中，大部分 C 端高频操作都是“查询我的订单列表”，因此通常选用 `buyer_id`（买家 ID）作为分片键。
- **优势**：同一个买家的所有订单都落入同一个物理库中，分页查询只需路由到单库完成，主表与详情表也可以按同一规则共存，保留了单库内的本地事务能力。

#### 2. 非分片键查询的破局方案
业务上不可避免地会有非分片键查询（例如卖家按 `seller_id` 查店铺订单，或者客服按 `order_id` 查单）：
- **买家库 + 卖家库异构双写（读写分离与 CQRS）**：面向买家的高频交易写入买家库；通过 Binlog 异步同步，将数据按照 `seller_id` 重新分片写入一套专供卖家后台查询的“卖家库”或 ES，实现读写与维度隔离。
- **基因法（Gene Method）**：生成 `order_id` 时，将 `buyer_id` 的后几位哈希基因嵌入到 `order_id` 的末尾。这样根据订单号查询时，截取后几位就能直接反解出该订单所在的分库编号。

#### 3. 全局唯一 ID 方案
分库后各库原生的自增主键必然冲突，必须引入全局分布式 ID：
- **雪花算法（Snowflake）**：64 位整数，包含时间戳、机器工作节点 ID 和序列号，高性能且趋势递增。
- **号段模式（如 Leaf / UidGenerator）**：利用独立数据库按步长批量分派 ID 号段并缓存在本地内存，兼顾高性能与绝对递增。

#### 4. 平滑扩容与不停机数据迁移
- **预分区**：一开始可以先按 `hash(buyer_id) % 1024` 划分为 1024 个逻辑分片，初期多个逻辑分片挂载在少数物理库上，后续扩容只需按分片迁移，不需要重新散列全量数据。
- **双写平滑迁移四步法**：
  1. **存量同步**：开启新库，全量导出历史数据并导入新库；
  2. **增量追平**：通过 Binlog 增量实时同步写入新库，追平时间差；
  3. **数据校验**：对比新旧库数据一致性，确认增量无延迟；
  4. **灰度切流**：先切读取流量验证，无误后关闭旧库双写，完成最终切换。

## 二、 真实场景题：支付成功但状态未更新

朋友记不清楚具体的题是什么，这里分享一道，与本次面试无关。

> **场景还原**：用户付款后，第三方支付平台回调或支付成功消息被重复投递了两次。用户刷新订单详情页，页面仍然显示“待支付”。你该如何排查？

这是一道非常经典的端到端线上故障排查题。排查这类问题切忌盲目猜测代码逻辑，必须建立**“自底向上、先查主库分流定界”**的排查链路：

```text
用户反馈：付款成功但刷新页面仍显示【待支付】
                  │
                  ▼
第一步：根据支付流水号，直接查询【订单主库】的权威数据状态
       ├── 分支 A：主库状态仍为【待支付】（排查上游链路与消费端写入）
       │     ├── 1. 查监控/日志：支付平台回调 Webhook 是否正常到达网关？
       │     ├── 2. 查消息队列：支付完成消息是否入队？消费者是否出现堆积或断连？
       │     ├── 3. 查异常日志：更新事务是否由于死锁、字段校验等异常导致回滚？
       │     └── 4. 查状态流转：更新 SQL 的 CAS 条件（WHERE status = 'PENDING'）是否匹配？
       │
       └── 分支 B：主库状态已变成【已支付】（排查下游链路与读取展示端）
             ├── 1. 查前端/网关缓存：页面是否命中了 CDN 缓存、浏览器本地缓存或网关层响应缓存？
             ├── 2. 查 Redis 缓存：订单详情的缓存是否未能正常清除或被旧请求覆盖？
             └── 3. 查从库延迟：订单查询接口是否读取了只读从库？主从复制是否存在秒级延迟？
```

### 1. 分支 A 排查重点：为什么主库没有更新？
- **消息是否正常消费**：通过分布式链路追踪（Trace ID）或日志系统，检查该笔 `payment_id` 对应的 MQ 消息是否到达了消费端，消费端线程池是否打满，或者消费者是否在频繁抛出未捕获异常。
- **状态机流转阻断**：查看更新订单的 SQL。如果前置逻辑已经被其他前置状态改动（例如在回调之前系统自动触发了超时关单），导致 `WHERE status = 'PENDING'` 更新影响行数为 0，更新未生效。
- **事务与幂等拦截误杀**：检查第二次重复投递的消息是否触发了幂等拦截机制，而防重拦截代码中是否误将“尚未完成订单更新”的第一次请求一起屏蔽。

### 2. 分支 B 排查重点：主库已更新，为什么用户看不到？
- **主从同步延迟（Replication Lag）**：很多系统的查询接口配置了读写分离。用户付款完成后通常在 1 秒内立即主动刷新页面，如果此时从库正在回放大量大事务产生延迟，读接口从从库拉取到的依然是旧的“待支付”状态。针对“支付完成跳转”这种对实时性要求极高的场景，查询必须**强制路由读主库**。
- **Redis 缓存失效异常**：更新主库后，删除对应订单详情缓存的操作可能失败或超时，而接口直接命中了旧的 Redis 缓存。

### 3. 副作用核对（幂等防护）
由于题目明确指出“消息投递了两次”，在解决显示问题的同时，必须立即核查**伴生业务流水**（如积分发放、赠送优惠券、通知发货系统等）：
- 检查积分记录与发货请求是否由于重复消费产生了多次触发；
- 确认流水表中是否存在唯一的 `payment_id` 约束，确保系统的最终一致性未被破坏。

## 三、 算法：滑动窗口最大值

### 题目说明 (LeetCode 239)

应该是非 hot 100 。

题目描述：给定一个数组 `nums` 和一个整数 `k`，每 `k` 个数返回一个最大值。

**面试现场细节**：先与面试官确认窗口滑动方式。
- 若为“每 $k$ 个数独立分一组”（如 `[1, 3], [2, 5]`，`k=2`），属于简单分段求最大值，直接每段线性遍历即可；
- 若为标准的“窗口每次向右移动一格”（滑动窗口），则为经典的滑动窗口问题，以下给出**基于单调双端队列（Monotonic Deque）**的标准解法。

### 算法思路

核心思路是维护一个**双端队列（Deque）**，队列中存放数组下标，下标对应的元素值从队首到队尾保持**严格单调递减**：

1. **移出过期元素**：新窗口左边界为 `left = i - k + 1`。若队首下标 `< left`，说明它已经滑出窗口范围，从队首移出。
2. **淘汰无用元素**：新元素 `nums[i]` 入队前，若队尾下标对应的元素 $\le nums[i]$，说明只要新元素在窗口内，前面较小的旧元素永远不可能成为最大值（它不仅比新元素小，而且会比新元素更早离开窗口），因此果断从队尾循环弹出。
3. **新元素入队**：将当前下标 `i` 压入队尾。
4. **收集结果**：当窗口形成后（即 `i >= k - 1`），队首下标对应的元素必然是当前窗口的最大值，直接追加到结果数组中。

### 逐步执行状态追踪表

以 `nums = [1, 3, -1, -3, 5, 3]`, `k = 3` 为例，直观展示滑动过程中的队列内部变化：

| 遍历下标 $i$ | 当前元素 `nums[i]` | 窗口左边界 $left$ | 队列操作说明 | 队列保存下标 (对应值) | 当前窗口最大值输出 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **0** | `1` | `-2` | 队列为空，下标 0 直接入队 | `[0]` (`[1]`) | 窗口未形成 |
| **1** | `3` | `-1` | $3 > 1$，弹出队尾下标 0；下标 1 入队 | `[1]` (`[3]`) | 窗口未形成 |
| **2** | `-1` | `0` | 队首 1 未过期；$-1 < 3$，直接入队 | `[1, 2]` (`[3, -1]`) | **3** (`result[0]`) |
| **3** | `-3` | `1` | 队首 1 未过期；$-3 < -1$，直接入队 | `[1, 2, 3]` (`[3, -1, -3]`) | **3** (`result[1]`) |
| **4** | `5` | `2` | 队首下标 1 过期（$1 < 2$），弹出；<br>$5 > -3$ 且 $5 > -1$，依次弹出队尾 3, 2；下标 4 入队 | `[4]` (`[5]`) | **5** (`result[2]`) |
| **5** | `3` | `3` | 队首 4 未过期；$3 < 5$，直接入队 | `[4, 5]` (`[5, 3]`) | **5** (`result[3]`) |

### 复杂度分析

- **时间复杂度**：**$O(n)$**。虽然代码中有 `for` 循环嵌套 `while`，但分析不能只看层数。数组中每个下标最多只会被压入队列一次，且最多只会被弹出队列一次。整个算法过程中，所有的入队和出队操作总次数上限严格为 $2n$，因此**平摊时间复杂度（Amortized Time Complexity）**为严格的 $O(n)$。
- **空间复杂度**：**$O(k)$**。双端队列中保存的下标数量不会超过窗口大小 $k$。

### 代码实现

#### Java 实现

```java
import java.util.ArrayDeque;
import java.util.Deque;

class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        if (nums == null || k <= 0 || k > nums.length) {
            return new int[0];
        }

        int[] result = new int[nums.length - k + 1];
        // 队列中存放数组下标，维持下标对应的值从队首到队尾单调递减
        Deque<Integer> deque = new ArrayDeque<>();

        for (int i = 0; i < nums.length; i++) {
            int left = i - k + 1;

            // 1. 移出滑出窗口左侧边界的队首元素
            if (!deque.isEmpty() && deque.peekFirst() < left) {
                deque.removeFirst();
            }

            // 2. 淘汰队列尾部小于等于当前值的元素（维持单调递减）
            while (!deque.isEmpty() && nums[deque.peekLast()] <= nums[i]) {
                deque.removeLast();
            }
            deque.addLast(i);

            // 3. 窗口形成后，队首即为当前窗口的最大值
            if (left >= 0) {
                result[left] = nums[deque.peekFirst()];
            }
        }
        return result;
    }
}
```

#### Go 实现

```go
package main

func maxSlidingWindow(nums []int, k int) []int {
    if k <= 0 || k > len(nums) {
        return []int{}
    }

    result := make([]int, 0, len(nums)-k+1)
    // 使用切片模拟双端队列，存放数组下标
    deque := make([]int, 0, k)

    for i, value := range nums {
        left := i - k + 1

        // 1. 移出滑出窗口左侧边界的队首元素
        if len(deque) > 0 && deque[0] < left {
            deque = deque[1:]
        }

        // 2. 淘汰队列尾部小于等于当前值的元素
        for len(deque) > 0 && nums[deque[len(deque)-1]] <= value {
            deque = deque[:len(deque)-1]
        }
        deque = append(deque, i)

        // 3. 窗口形成后，记录当前窗口最大值
        if left >= 0 {
            result = append(result, nums[deque[0]])
        }
    }
    return result
}
```
